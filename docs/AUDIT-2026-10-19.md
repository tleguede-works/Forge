# Audit of 2026-10-19

First end-to-end pass of item I-006: reference graph, phase-by-phase walk, order review, escape-hatch review, with a regression test for every hole closed. Nothing here replaces a run on a real project (item I-005).

## Method

1. Built a reference graph over 94 files: skills, agents, reference files, CLI commands, deliverables, phase-to-skill mapping.
2. Walked each phase from `forge status` as an agent would, listing every instruction and the check behind it.
3. Compared phase order with what each phase reads and produces.
4. Tried each suspected hole against the CLI before fixing it.

## Result of the reference graph

- No reference file is cited nowhere, and no reference points to a file that does not exist.
- Every agent and skill is named by at least one other component, but eleven of the fifteen deliverable names had no template (now written, see below).
- Every `forge <command>` named in a skill or agent exists. `forge kit` and `forge lint-rules` are named in no skill: `kit` runs through `status` and the approval gate, `lint-rules` is a maintenance command, so both stay.

## Decisions taken by the owner on 2026-10-19 (applied)

1. **Contract and roadmap.** The contract holds collaboration terms only, and `roadmap` is now a client touchpoint where scope, priorities and cost are agreed.
2. **Release scoping in design.** Releases are named MVP, R1, R2 (V1 and V2 clashed with validation IDs; found by a test). Every screen-map row carries a `release` that must be a heading of the roadmap.
3. **Structure and minimum content.** Registration checks the required sections of 12 deliverables and refuses empty sections and `<fill>` markers. `forge template <name>` prints the skeleton, and `tests/templates.sh` keeps the CLI and the skill templates in step.
4. **Regulatory phase.** First version implemented (item I-004). The code-review step before commits (item I-001) is still to study.

## Left to judgement (unchanged, named)
