# Internationalization & Strings

## Commands

{{regeneration command}}    {{e.g. regenerate localization files — required after ANY change to a source translation file}}

## One Source

- **Every user-facing string lives in the localization module.** No string
  literal in a component, a screen, or a validation message.
  - Verify: `{{grep}}` returns no inline user-facing literals.
- **Add the key to the source-of-truth file first**, then use it. An inline
  literal is a violation even when the module doesn't have the string yet
  (`architecture.md` §Centralized Concerns).
- **The source-of-truth locale is the project's native language**, and every
  other locale derives from it.

## Keys, Not Phrases

- **A key names a meaning, not a sentence.**
  `{{strings.product.addToCart}}` — not `{{strings.product.addToCartLabel}}`
  spelled out in English.
- **Never interpolate a whole sentence at the call site.** A sentence assembled
  from fragments in code cannot be reordered by a translator, and word order is
  not universal.
  - Wrong: `` `${count} items in your cart` ``
  - Right: `{{strings.cart.lineCount(count)}}` — the translation owns the
    sentence, the code owns the value.
- **Parameterised messages are the norm for anything with a value in it** —
  counts, names, dates, amounts.
- **No interpolation inside a key.** A key containing a value is a different
  string every time, and the translation file becomes unusable. Parameterise in
  the value, not the key.
- **Plural forms are handled by the localization layer**, not by
  `{{count === 1 ? ... : ...}}` in a component.

## Regeneration

- **Generated localization output is committed and regeneration is a mandatory
  step, not a convenience.** {{e.g. "run the generator after ANY change to a
  source file; if you forget, the build fails."}}
- **The generated files are part of the change.** A commit that edits a source
  translation file without the regenerated output is an incomplete commit.
- **Never hand-edit a generated file.** The next regeneration overwrites it.

## Source & Translations

| | File | Role |
|---|---|---|
| Source of truth | `{{path}}` | the native language; every key is defined here first |
| Translations | `{{paths}}` | one per locale; may lag the source |
| Generated | `{{path}}` | committed; never hand-edited |
| Config | `{{path}}` | declares directories, source file, output class, fallback |

- **Minimum viable coverage: the source locale plus at least one
  translation.** A locale with an empty file is worse than an absent one — it
  looks done.
- **The source value is the fallback** for a key not yet translated, so a
  missing translation degrades to readable text rather than a raw key.
- **Feature-scoped accessors are an option, not a mandate** — a thin wrapper
  that scopes a feature's keys, when a feature has enough of them to justify
  it. Do not build one per feature by default.
- **A key is added once and reused.** If two features need the same string, they
  share the key. Duplicated keys drift into inconsistent wording.

## Formatting Is Not Translation

- **Dates, times, numbers, and currency are formatted by the platform's
  formatter**, using the active locale. Never assembled by string
  concatenation.
- **One formatter module per project.** If two components format a date the
  same way, that's the second occurrence — extract it
  (`architecture.md` §Reusability Threshold).
- **Currency is a structured value** and the currency comes from the data, not
  from a hardcoded symbol (`data-and-state.md` §Money).
- **A number is never a string when it crosses a boundary** — format at the
  edge, not in the middle of a component.
- {{e2e}}: **translate validation messages too.** They are user-facing, and they
  are usually the last thing translated and the first thing a user reads when
  something goes wrong.

## When Blocked

- **If a string cannot be expressed as a parameterised message in the source
  language:** check whether the problem is a missing parameter, not a hardcoded
  concatenation. Concatenation is never the answer.
- **If a locale needs a plural form the default mechanism doesn't cover:** use
  the platform's plural/select mechanism. Don't approximate with a conditional
  in a component.
- **If a key's meaning is ambiguous** — one key serving two contexts that would
  translate differently: split the key. Two precise keys beat one vague one.
- Never: inline a user-facing string "temporarily"; hand-edit a generated file;
  concatenate translated fragments; ship a locale file that's empty.
